# Chronos — техническое задание

**Версия:** 1.0  
**Тип:** демонстрационный прототип мобильного веб-приложения  
**Срок разработки и подготовки защиты:** около 5 дней  
**Команда:** 2 человека

## 1. Назначение и цель

Chronos — приложение для учёта времени, затраченного на повседневные занятия. Пользователь запускает таймер выбранной категории, переключает занятия и анализирует историю и распределение времени за день или неделю.

Цель текущей версии — создать визуально качественный, действительно работающий прототип для демонстрации и защиты учебного проекта. Это не коммерческий продукт.

## 2. Технологии и ограничения

- HTML5, CSS3, JavaScript (без обязательного фреймворка).
- Разработка в VS Code; интерфейс в первую очередь для смартфона, с адаптацией под десктоп.
- Без обязательного сервера, авторизации и платных сервисов.
- Публикация статического сайта на GitHub Pages либо аналогичном бесплатном хостинге.
- Возможная упаковка в Android APK через Capacitor — **не входит в обязательный объём**.
- Все основные функции должны работать без подключения к интернету после загрузки приложения, насколько это позволяет выбранный способ размещения; полноценный офлайн-режим/PWA не обязателен.
- Интерфейс и тексты — на русском языке.

## 3. Функциональные требования (MVP)

### 3.1. Таймер и переключение занятий

1. Пользователь выбирает категорию и запускает таймер.
2. На экране отображается название активной категории и прошедшее время в формате `ЧЧ:ММ:СС`.
3. При остановке таймера создаётся запись активности с датой, временем начала и окончания.
4. При переключении категории текущая запись завершается, новая начинается автоматически.
5. Одновременно может работать только один таймер.
6. Текущее состояние таймера сохраняется при обновлении страницы; время рассчитывается по временным меткам, а не только по количеству вызовов `setInterval`.
7. Пауза необязательна: для MVP достаточно запуска, остановки и переключения.

### 3.2. Категории

- Начальные категории: «Учёба», «Работа», «Отдых», «Сон», «Спорт», «Другое».
- Добавление своей категории, изменение её названия и цвета.
- Цвет категории последовательно используется в карточках и диаграммах.
- Удаление категории допускается только с понятной обработкой связанных записей (например, запрет удаления при наличии записей); выбранное поведение зафиксировать в интерфейсе.

### 3.3. История активности

- Список записей за выбранный день: категория, начало, конец, продолжительность.
- Сортировка по времени начала.
- Ручное добавление, редактирование и удаление записей.
- Проверка корректности интервала: окончание позже начала; недопустимые пересечения с другими записями должны предотвращаться или явно обрабатываться.
- Для MVP одна запись относится к одному календарному дню. Если таймер пересекает полночь, запись при сохранении разделяется на интервалы по дням.

### 3.4. Календарь

- Выбор даты для просмотра истории.
- Удобная навигация между днями, выделение текущего и выбранного дня.
- Даты с активностями можно визуально отмечать.

### 3.5. Статистика

- **За день:** круговая/кольцевая диаграмма времени по категориям, легенда с длительностями и процентами.
- **За неделю:** столбчатый график суммарного учтённого времени по дням.
- Неделя начинается с понедельника; предусмотрено переключение недель.
- Статистика пересчитывается после изменения или удаления записей.
- При отсутствии записей показывается понятное пустое состояние, а не фиктивные показатели.
- Неучтённое время не считается отдельной категорией автоматически.

## 4. Экраны и навигация

1. **Главная:** активная категория, крупный таймер, запуск/остановка, быстрый выбор категорий, краткая сводка за сегодня.
2. **История:** выбранная дата, список записей, добавление и редактирование.
3. **Статистика:** кольцевая диаграмма по категориям и недельный график, переключатели периодов.
4. **Категории/настройки:** список категорий, создание и редактирование, управление демонстрационными данными.

Навигация — нижняя панель мобильного приложения. Все действия должны иметь видимые состояния и обратную связь; неработающих декоративных кнопок быть не должно.

## 5. Дизайн

- Современный мобильный интерфейс, аккуратная типографика, единая система отступов, цветов и радиусов.
- Приоритет — качество главного экрана, статистики и истории: именно они будут использоваться для скриншотов.
- Адаптация под ширину около 360–430 px и корректное отображение на компьютере.
- Читаемые подписи графиков, контрастные кнопки, понятные состояния пустых данных.
- Избегать шаблонной перегруженности: лишних градиентов, бессмысленных метрик, анимаций и декоративных блоков.
- Конкретную палитру, шрифты и референсы зафиксировать отдельно в `DESIGN.md` до окончательной стилизации.

## 6. Данные и хранение

### 6.1. Логическая модель

**Category**
- `id`: уникальный идентификатор;
- `name`: название;
- `color`: цвет в HEX.

**Activity**
- `id`: уникальный идентификатор;
- `categoryId`: ссылка на категорию;
- `startAt`: дата и время начала (ISO 8601);
- `endAt`: дата и время окончания (ISO 8601);
- `durationMs`: вычисляемая длительность (`endAt - startAt`), не независимый источник истины.

**AppState**
- `activeTimer`: `null` либо `{ categoryId, startAt }`;
- `selectedDate`: выбранная дата для интерфейса.

### 6.2. Выбор хранилища

**Решение пока открыто.** Для быстрого MVP предпочтителен `localStorage` или `IndexedDB`: они не требуют сервера. SQL Server/SSMS не использовать без отдельного обоснования, поскольку браузер не должен напрямую подключаться к SQL Server. SQLite возможен при изменении архитектуры, но не обязателен.

Данные активности не должны быть жёстко зашиты в логику интерфейса. Весь доступ к ним организовать через отдельный модуль хранения, чтобы можно было заменить реализацию позднее.

### 6.3. Демонстрационные данные

- Отдельный файл `demo-data.json` с реалистичными **синтетическими** записями за 7–14 дней.
- Кнопка «Загрузить демоданные» с подтверждением и понятным поведением при существующих записях (предпочтительно замена после подтверждения).
- Данные используются для демонстрации истории, календаря и графиков; их нельзя представлять как результаты реальных наблюдений.
- Предусмотреть возможность очистить данные и начать учёт заново.
- Желательно добавить экспорт/импорт JSON, если останется время; это необязательная функция.

## 8. Критерии приёмки

- Приложение запускается локально и открывается на смартфоне по опубликованной ссылке.
- Запуск, остановка и переключение таймера создают корректные записи.
- После обновления страницы активный таймер и сохранённая история не теряются.
- История фильтруется по дате; записи можно добавить, изменить и удалить.
- Пользовательские категории сохраняются и отражаются в статистике.
- Диаграммы отображают значения, соответствующие истории.
- Демоданные можно загрузить без ручного изменения исходного кода.
- Все четыре основных экрана доступны, интерфейс не ломается на мобильной ширине.
- Нет критических ошибок в консоли при основном сценарии.

## 9. Порядок реализации (5 дней)

| День | Задачи | Результат |
|---|---|---|
| 1 | Утвердить ТЗ и дизайн, создать структуру и навигацию | Красивый каркас экранов |
| 2 | Таймер, категории, сохранение | Рабочий учёт времени |
| 3 | История, календарь, редактирование | Управление записями |
| 4 | Статистика, демоданные, полировка | Заполненные и работающие графики |
| 5 | Проверка, исправления, публикация, скриншоты | Готовый прототип для защиты |

При нехватке времени приоритет: **таймер → сохранение → история → статистика → категории → расширенные настройки**. Визуальная целостность основных экранов обязательна.

## 10. Демонстрация и передача напарнику

Подготовить:

- исходники проекта и `README.md` с запуском;
- публичную ссылку на приложение (при успешной публикации);
- скриншоты главной, истории, статистики и категорий;
- короткий сценарий показа: загрузить демоданные → запустить таймер → переключить категорию → остановить → посмотреть историю → изменить запись → открыть статистику;
- описание того, какие функции реализованы, а какие оставлены за рамками MVP.

## 11. Отдельные материалы учебного проекта

**Не входят в программное ТЗ Chronos**, но должны быть подготовлены для защиты:

1. Сайт проекта с описанием, этапами и еженедельными публикациями (по требованиям методички — минимум одна публикация в неделю). Историю можно оформить ретроспективно, корректно обозначая реальные и плановые этапы.
2. Презентация с проблемой, целью, функциональностью, архитектурой, демонстрацией и результатами.
3. Текст выступления.
4. Комплект исходников, скриншотов и демонстрационных материалов.

## 12. Что пока не включаем

Регистрацию, облачную синхронизацию между устройствами, серверную СУБД, уведомления, сложную аналитику, интеграции с календарями, публикацию в Google Play и обязательную сборку APK. Эти возможности можно рассматривать после готовности MVP.
